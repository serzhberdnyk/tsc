# Protected hourly update contract

This Site is owner-private. Never change its audience. Cloudflare D1 is canonical and R2 retains source evidence. The original import is 134 records and 202 evidence objects; do not reimport it. The verified v2 baseline has 204 publications and five connected collectors. Source or UI publication does not itself enable a schedule. GET /api/data reports the saved scheduler configuration and latest batch separately from publication.

For an authorized unattended run, call Sites get_site for this exact linked Site. Use its current supported service access, if supplied, only in OAI-Sites-Authorization to current_live_url. Never create or rotate credentials automatically, persist them, or send them to source sites. If service access is unavailable, report the blocker and do not attempt unauthenticated writes. The update needs no local checkout, running PC or browser session.

POST /api/collect?source=all with X-Tenders-Action: collect and no body. The Worker processes one enabled source per request and saves progress. Repeat this same endpoint while continue_required is true, at most five steps, without choosing source names. Each HTTP request is bounded to one source with a 25-second network budget. A global two-minute renewable database lease excludes overlapping collection and import. The current UTC hour is the cycle key; repeating a completed cycle returns its saved receipt without external requests. If a response is uncertain or 409, GET /api/data and inspect collection before retrying. Do not clear a lease: after a canceled request wait for it to expire; legacy v3 leases can last 15 minutes. GET /api/maintenance exposes this protocol without a checkout. Never blindly repeat the POST. After completion, read GET /api/export and confirm collection.run_id, prior record IDs, per-source success/error state and persisted evidence. The API retains errors and previous successful times. A partially successful batch is not complete coverage.

Single-source technical/manual collection remains available via source=bidzaar, sibur, gk_nvm, nutep or rosmorport_azov_black_sea. The storefront has an owner-only “Обновить данные” control using the same five-step hourly-idempotent collection protocol. It reads back saved data after each step and shows source failures and partial coverage. No timer in the browser substitutes for the linked cloud schedule. GET /api/export remains an owner-protected technical backup. Never delete old data or evidence because a feed is empty or a source fails.

Each source is bounded to 25 seconds, 20 requests, >=600ms spacing; at most 8 Bidzaar filtered pages and 8 permitted detail cards, one SIBUR/NVM/NUTEP list, or two Rosmorport lists. HTTP 401/403, CAPTCHA, robots exclusions, TLS verification failure and unverified redirects stop that source pending manual review. Do not change routes or bypass controls. HTTP 429 stops the current pass and respects Retry-After; network/server/parser failures back off from one hour up to 24 hours, doubling on repeated failure. A later source Retry-After takes precedence. No automatic access occurs while next_retry_at is in the future. Independent sources continue.

All port publications remain list_only/HOLD; price inquiries for NMCK are separate from supplier selection. Unknown execution place and timezone remain unknown. No source account, subscription, API token, attachment download, bid or outreach is involved.

The supported Sites tool available in this environment links a cloud task, not a Worker cron trigger. Enable it only when this variant is accepted and Sites get_site confirms no matching linked automation. The schedule prompt should request the outcome and refer to this update contract; never include credentials. Preserve source settings and restrictions. After creation, save the returned hourly schedule metadata through the owner-protected POST /api/schedule (X-Tenders-Action: schedule): provider=sites_cloud_task, exact task_id, enabled, interval_minutes=60, timezone=Asia/Bangkok, explicit starts_at and verified_at. This records an externally verified schedule; it does not create one. next_planned_at is computed from saved timing, not a claim that the next run has executed. Creation proves only saved scheduling. Verify an actual run separately. Do not substitute a chat reminder, browser timer or local operating-system job.
